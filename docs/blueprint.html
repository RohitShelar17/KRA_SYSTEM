Enterprise KRA & Performance Platform

A daily work-tracking and performance-management system for a multi-department organisation: employees record where their working hours went, managers review and rate that work, and the platform rolls it up into daily, monthly, quarterly and annual scores against configurable KRAs and KPIs.

Section 01

Application architecture

A single Spring Boot service, a React SPA, and MySQL. The service is a modular monolith: strict package boundaries per domain so that scoring, work logging and identity can later be split out, without paying the cost of distributed transactions on day one.

React SPATypeScript · MUI · TanStack Query · Recharts · served by Nginx
REST / JSON/api/v1 · JWT bearer · OpenAPI 3 contract · CORS-restricted
Controllerrequest binding, validation, HTTP status mapping — no business logic
Servicetransactions, authorisation rules, domain logic, orchestration
EnginePerformanceCalculationService, TimesheetValidator, WorkflowEngine
RepositorySpring Data JPA, projections, native queries for report aggregates
MySQL 8Flyway-migrated · InnoDB · snapshot tables for computed scores

Cross-cutting concerns

  • Security filter chain — JWT parsing, tenant/company resolution, method-level @PreAuthorize.
  • Audit — JPA entity listener for created/updated columns, plus an explicit @Audited AOP aspect that writes old/new values for regulated entities.
  • Scheduler — nightly and month-end jobs producing performance snapshots; guarded by a DB lock so multiple instances do not double-run.
  • Cache — Redis for permission sets, company settings, rating bands and the active formula config; these are read on nearly every request and change rarely.
  • Exception translation — one @RestControllerAdvice producing a single error envelope.

Why snapshots, not on-the-fly scoring

Performance figures are read constantly (dashboards, reports, appraisal screens) and change rarely. Every score is computed once by the engine and stored in daily_performance, monthly_performance, quarterly_performance and annual_performance with the formula version and input breakdown that produced it. Recalculation is an explicit, audited action — never an implicit side effect of a page load. This also means a finalised appraisal cannot silently change when someone edits a formula six months later.

Section 03

User roles and permissions

Roles are rows, not enum constants in code. Authorisation is checked against permissions (WORKLOG_APPROVE, KRA_ASSIGN, PERFORMANCE_FINALIZE), and roles are named bundles of permissions that an administrator can edit. Code never asks “is this user an HR admin”; it asks whether they hold the permission.

Scope, not just permission. “dept” and “reports” above are data scopes. A permission answers what a user may do; a scope answers to whom. Every query that returns employee data passes through AccessScopeResolver, which returns the set of employee ids the caller may see: SELF, REPORTS (direct + indirect via the reporting hierarchy), DEPARTMENT, or ORGANISATION. Repository methods take that set. This is the single control that stops a manager reading another team’s appraisals.

Section 04

Employee workflow

Log in→Dashboard→Add work entries→Update tasks→Submit day→Manager review→Self assessment
  1. Daily. Opens the dashboard: today’s timeline, assigned tasks, unallocated hours, pending manager comments.
  2. Adds work entries as the day proceeds — time slot, task, category, KRA/KPI link, status, completion percentage. The timeline updates live and shows unaccounted gaps.
  3. Marks tasks complete, records actual hours against estimates.
  4. Submits the day before the configured cut-off. After submission the log is read-only unless the manager requests modification.
  5. Monthly. Reviews the computed monthly score and its input breakdown; raises a query with the manager if a figure looks wrong.
  6. Cycle end. Completes the self-assessment: achievements, challenges, skills gained, training needed, goals, self rating.
  7. Reads manager and department-head feedback once the cycle is finalised, and sees the final rating band.

An employee can never edit a computed score, another person’s log, or a KRA weightage.

Section 05

Reporting manager workflow

  1. Morning. Team dashboard shows who has and has not submitted yesterday’s log, plus pending approvals and overdue tasks.
  2. Reviews submitted logs: approve, reject with reason, or request modification. Every decision is stored with a comment and timestamp in work_log_approvals.
  3. Assigns tasks with estimates, due dates and KRA/KPI linkage.
  4. Records the daily or weekly quality rating and manager rating that feed the score formula. These are the only score inputs a manager controls directly.
  5. Cycle end. Completes the evaluation form — per-KRA rating, per-KPI achievement confirmation, plus quality, productivity, timeliness, teamwork, communication, initiative, problem solving and discipline — and writes narrative feedback.
  6. Submits the review upward to the department head.
A manager cannot rate their own record, cannot approve their own logs, and cannot see employees outside their reporting subtree. Self-review attempts are rejected at the service layer, not just hidden in the UI.
Section 06

HR workflow

  1. Creates employees, assigns department, team, designation and reporting manager; the user account and role assignment are created in the same transaction.
  2. Maintains KRA and KPI templates per designation (Software Developer, QA Engineer, Sales Executive, HR Executive, Manager) and applies a template when someone joins or changes role.
  3. Opens a performance cycle — monthly, quarterly or annual — which sets the self-assessment and review windows and triggers notifications.
  4. Monitors submission compliance: who has not filed logs, which managers have not reviewed, which cycles are stalled.
  5. Runs the review pass after department heads, applies any authorised manual adjustment (reason mandatory), and finalises the cycle, which freezes the scores.
  6. Generates organisation and department reports and exports them for the appraisal committee.
Section 07

Administrator workflow

  • Defines the organisation: departments, teams, designations, working hours, week-off pattern, holiday calendar.
  • Configures the performance formula — which parameters count and at what weightage — with a hard validation that weightages total 100%. Saving a new configuration creates a new version; existing snapshots keep the version they were computed under.
  • Configures rating bands (Outstanding, Excellent, Good, Meets Expectations, Needs Improvement, Unsatisfactory) with their score ranges.
  • Manages roles and permission bundles, task categories, activity categories and productivity classification rules.
  • Reviews audit logs, active sessions and scheduled-job outcomes.
Section 08

Daily work tracking workflow

This is the data-collection heart of the system; everything downstream is arithmetic on it.

Entry validation, in order

  1. Date is not in the future and not older than the configured back-dating window (default 3 days; back-dating beyond it needs manager approval).
  2. The day is not already submitted or approved.
  3. endTime > startTime; both fall inside the company working window unless overtime is enabled for the employee.
  4. No overlap with an existing entry for that employee and date — checked with a half-open interval test (newStart < existingEnd AND newEnd > existingStart), backed by a covering index on (employee_id, work_date, start_time).
  5. Duration is computed server-side in minutes; a client-supplied duration is ignored.
  6. Total logged minutes do not exceed working minutes plus the permitted overtime allowance.
  7. A KRA/KPI link, if given, must be currently assigned to that employee.

Derived day totals

FigureDerivation
Office hoursFrom company settings and the employee’s shift — e.g. 09:00–18:00 = 9.0 h
Logged hoursSum of all entry durations
Productive hoursSum where the activity category is flagged productive
Meeting hoursSum where category type = MEETING
Break hoursSum where category type = BREAK
Unallocated hoursOffice hours − logged hours, floored at zero
Overtime hoursLogged hours − office hours, floored at zero

Submission and approval

DRAFT→SUBMITTED→UNDER_REVIEW→APPROVED | REJECTED | MODIFICATION_REQUESTED→DRAFT

Approval is a company setting: when it is off, submission alone makes the day final and the daily score is computed without a manager component. Every state change writes a row to work_log_approvals so the history is reconstructible.

Section 09

KRA and KPI workflow

Template per designation→Assigned to employee→Targets per period→Actuals accrue→Achievement %→Score
  1. HR or the department head builds a KRA template for a designation. KRA weightages within a template must total exactly 100% — enforced on save, not merely warned about.
  2. Each KRA carries KPIs whose weightages must total 100% within that KRA.
  3. Assigning the template to an employee copies the KRAs and KPIs into employee_kras / employee_kpis for a specific period. Templates evolve; a signed-off assignment must not.
  4. A manager may adjust an individual’s weightages where authorised; the 100% rule still applies and the change is audited.
  5. Targets are set per period — daily, weekly, monthly, quarterly, annual — in the KPI’s measurement type: percentage, numeric, currency, hours, count, boolean, rating or custom.
  6. Actuals arrive three ways: automatically from work-log and task aggregates where the KPI declares a source, by manager entry, or by an integration. The source is recorded on each actual.
Shipped with one addition. A KPI can declare where its actual comes from. Three sources read Phase 2 data directly — productive-hours ratio from the timesheet, and task completion and on-time rates from the task board — so those figures are measured rather than asserted, are never read into the future, and refuse manual entry. The cross-module reads go through ports the KRA module declares, implemented in the modules that own the data.

Achievement, by direction

// higher-is-better (revenue, completion rate)
achievement % = min(actual / target × 100, cap)

// lower-is-better (bug resolution time, reopened bug %)
achievement % = min(target / actual × 100, cap)

// boolean
achievement % = met ? 100 : 0

cap defaults to 120 — over-achievement is rewarded, but bounded

KRA score is the weighted mean of its KPI achievements; overall KRA achievement is the weighted mean of KRA scores. Any KPI with no target for the period is excluded and its weight redistributed, so a missing target cannot silently score zero.

Snapshot lifecycle

COMPUTED→SELF_ASSESSED→MANAGER_REVIEWED→HEAD_REVIEWED→HR_REVIEWED→FINALIZED

Only PERFORMANCE_FINALIZE holders move a snapshot to FINALIZED, and only PERFORMANCE_REOPEN holders move it back — with a mandatory reason, written to the audit log. Recalculation refuses to touch a FINALIZED row.

Every snapshot stores its formula_config_version and a JSON score_breakdown holding each parameter’s raw value, weight and contribution. That breakdown is what the UI shows when someone asks why they scored 84 rather than 86, and it makes a score defensible in an appraisal conversation.

Built differently to this sketch, deliberately. Submission and approval turned out to be per day, not per entry, so a work_log_days header now owns the status and the cached day totals and daily_work_logs rows hang off it. Storing the submission status on every entry would have duplicated it N times per day and let the copies drift. The entry keeps its own status for the progress of that piece of work, which is a different question from whether the day has been filed.

Rules that the schema itself enforces

  • UNIQUE(employee_id, work_date, start_time) stops duplicate entries; overlap is enforced in the service layer, since MySQL has no exclusion constraint.
  • UNIQUE(employee_id, perf_year, perf_month) makes snapshot generation idempotent — a re-run updates rather than duplicates.
  • UNIQUE(employee_code, company_id) and UNIQUE(email) on employees.
  • Reporting hierarchy is effective-dated (valid_from, valid_to), so a past appraisal still resolves the manager who actually held the relationship.
  • Weightage totals are checked in the service layer within the same transaction as the write — a CHECK constraint cannot span rows.

daily_work_logs, daily_performance, notifications and audit_logs are the growth tables. All four are partitioned by RANGE on year from the start, and the archival job moves partitions older than the retention window to history tables. No list endpoint returns unpaged results; the default page size is 25 and the maximum is 200.

Partitioning is deferred, deliberately and in writing. MySQL refuses foreign keys on a partitioned table in either direction, and requires the partition column in every unique key including the primary key. Partitioning therefore costs either referential integrity or a changed primary key on tables — daily_work_logs, notifications, daily_performance — whose foreign keys are worth more than the partitioning until they are very large. audit_logs is the exception: it carries no foreign keys by design, nothing references it, and docs/ops/partition-audit-logs.sql holds the script, the trigger for running it (roughly ten million rows) and the yearly reorganise-and-drop cycle. Shipping it as an operational script rather than a migration is the point: it rebuilds a large table and belongs in a maintenance window, not in a deploy. What did ship is indexes for the access paths Phases 5 and 6 added, and a nightly retention pass that clears read notifications only.

Shipped, with the appraisal as the noun. The sketch hung these endpoints off /self-assessments and /manager-reviews; the built API hangs them off the appraisal record, because every one of those actions needs the same three checks — is this cycle’s window open, is the appraisal on that step, and may the caller see this employee. Two rules the sketch left implicit: only a submitted review reaches the score, so a draft is nobody’s judgement yet; and an unrated competency is left out of the derived overall rather than counted as a zero — the same exclusion rule the engine applies to a parameter it cannot measure. The KRA and KPI ratings stay out of that mean as well, since the engine measures both directly and a reviewer’s view of them should not count twice. The workflow itself is a table: three configurations are refused (nothing active, self assessment alone, an optional last step), and an appraisal sitting on a step deactivated underneath it moves to the next configured step rather than stranding.

Section 19

Performance calculation formulas

Nothing below is hard-coded. Parameters, weights and caps are rows in performance_formula_parameters, versioned as a set. The engine reads the active version, validates that weights sum to 100, and refuses to run otherwise.

Component scores, each normalised to 0–100

task_completion = completed_tasks / assigned_tasks × 100
productivity = productive_hours / expected_hours × 100 (capped at 100)
kpi_score = Σ( kpi_achievement × kpi_weight ) / Σ kpi_weight
kra_score = Σ( kra_kpi_score × kra_weight ) / Σ kra_weight
quality_score = manager quality rating × 20 (1–5 scale → 0–100)
manager_rating = manager overall rating × 20
timeliness = on_time_completions / completed_tasks × 100

Daily

daily_score =
  task_completion × 30%
 + kra_achievement × 25%
 + productivity    × 20%
 + quality_score   × 15%
 + manager_rating × 10%
Days with no submitted log score 0 for productivity but are excluded
from the monthly average if the day is a holiday, week-off or approved leave.

Monthly

monthly_score =
  avg(daily_score over working days) × 40%
 + monthly_kra_achievement          × 25%
 + monthly_kpi_achievement          × 20%
 + manager_monthly_rating           × 15%
consistency factor: if log-submission rate < threshold (default 80%),
apply the configured penalty multiplier and record it in the breakdown.

Quarterly and annual

quarterly_score =
  avg(3 monthly scores) × 60%
 + quarterly_kpi_achievement × 25%
 + manager_quarterly_rating  × 15%

annual_score =
  avg(4 quarterly scores)  × 50%
 + annual_kra_achievement  × 20%
 + annual_kpi_achievement  × 15%
 + manager_annual_rating   × 10%
 + department_head_rating  × 5%
Self-assessment is recorded and shown alongside, but carries 0% weight
by default — configurable, deliberately off.
Shipped with one rule the sketch left implicit. A parameter the engine cannot measure is excluded and its weight redistributed across the rest, exactly as an untargeted KPI is — a missing manager rating is an unfilled form, not a bad month. The stored breakdown records the skipped parameter, the reason, and the weight that moved, so a redistributed score still adds up on screen. Non-working days with nothing logged are not scored at all, keeping weekends out of the monthly average, while a day somebody worked and filed is scored whatever the calendar says.

Rating bands (defaults, editable)

RangeBandMeaning
90–100OutstandingConsistently exceeds every target
80–89ExcellentExceeds most targets
70–79GoodMeets targets, exceeds some
60–69Meets ExpectationsMeets the role’s requirements
50–59Needs ImprovementImprovement plan required
< 50UnsatisfactoryFormal review required

Bands are validated on save to be contiguous and non-overlapping across 0–100, so no score can fall between two bands.

Security architecture

ControlImplementation
AuthenticationStateless JWT. Access token 15 min, refresh token 7 days, stored hashed in refresh_tokens and rotated on every use; reuse of a rotated token revokes the whole family.
PasswordsBCrypt, strength 12. Policy enforced on set. Never logged, never returned, never compared outside the encoder.
Authorisation@PreAuthorize("hasAuthority('WORKLOG_APPROVE')") at the service layer, plus AccessScopeResolver for row-level scope on every employee-bound query.
Brute forceFailed-attempt counter per account with progressive lockout; per-IP rate limit on /auth/*.
InjectionJPA parameter binding throughout; native report queries use named parameters and a whitelist for any dynamic sort or filter column.
XSSReact escapes by default and dangerouslySetInnerHTML is banned; server-side sanitisation on rich-text remarks; strict Content-Security-Policy header.
HeadersHSTS, X-Content-Type-Options, X-Frame-Options DENY, Referrer-Policy, Permissions-Policy.
CORSExplicit origin allowlist per environment; credentials allowed only for the SPA origin.
UploadsExtension and MIME allowlist, size cap, stored outside the web root with generated names, virus-scan hook.
Sessionsuser_sessions records device, IP and last-seen; a user can list and revoke their sessions, an admin can revoke anyone’s.
SecretsEnvironment variables only. No credential, JWT secret or SMTP password in any committed file.
Score integrity is a security requirement, not a UX one. No endpoint accepts a computed score as input. Adjustments go through /performance/{id}/adjust, which demands a reason, records old and new values with the actor, and is unavailable once the snapshot is FINALIZED.
Shipped, with the rate limit in process. The per-IP window in front of /auth/* is a Caffeine-backed counter inside the application rather than a shared store: this deployment is a single instance, and a limiter that works beats a distributed one that is configured and unreachable. Behind more than one instance the window becomes per-instance — a real limitation, and the fix is Redis, not a bigger map. Authenticated traffic is deliberately not throttled: it is attributable and scope-limited already, and a manager approving forty timesheets on a Monday is not an attack. The API's Content-Security-Policy is default-src 'none' because it serves JSON and nothing else. Under the prod profile the application checks its own configuration at startup and refuses to run with the shipped signing key, a short one, an empty database password, or CORS still allowing localhost — naming every problem rather than stopping at the first.
Section 21

Notification architecture

Domain event→NotificationService→Template render→Channel fan-out→in-app + email

Services publish Spring application events (WorkLogSubmittedEvent, TaskAssignedEvent, PerformanceFinalizedEvent); an async listener resolves recipients, renders a template and dispatches per channel. Channels implement one NotificationChannel interface, so adding push, WhatsApp or Teams later is a new implementation and a row in the channel preference table — no change to the callers.

EventRecipientChannels
Daily log not submitted by cut-offEmployee, then manager next morningIn-app, email
Work log approved / rejected / returnedEmployeeIn-app
Task assigned or reassignedAssigneeIn-app, email
Task due tomorrow / overdueAssignee, manager on overdueIn-app
Monthly score publishedEmployee, managerIn-app, email
Self-assessment window open / closingEmployeeIn-app, email
Review pending beyond SLAManager, escalating to headEmail

Delivery is retried with backoff and recorded per recipient per channel, so “nobody told me” is an answerable question. Digest mode collapses repeat reminders into one daily email.

Shipped, with one contract instead of a class per event. Services publish a single NotificationRaised event carrying the event key, the recipients and the placeholder values; the listener runs AFTER_COMMIT and @Async, so nobody is told about an approval that then rolled back and no channel adds latency to the request that caused it. Recipients are resolved at the publishing site rather than inside the notification module, because that is where the domain knowledge lives — the work-log module knows the reviewing manager, the appraisal module knows whose step is next. The wording lives in notification_templates, so an administrator can reword a message without a release, and a placeholder the event did not supply is left as written rather than printed as "null". Email has no mail sender in this deployment: its deliveries record SKIPPED with the reason rather than pretending to send. Daily scores are deliberately silent — a notification for every person every night would train people to ignore the feed — and the nightly reminders check that nobody has already been told today.
Section 22

Reporting architecture

One registry, fifteen definitions. A report definition declares its key, required permission, filter schema, column set and the query provider; ReportService resolves the definition, applies the caller’s access scope, runs the query and hands the result to a renderer. Adding a report is a new definition class, not a new controller.

daily-workemployee-timesheetdepartment-timesheettask-completionproductivitymonthly-performancequarterly-performanceannual-performancekra-performancekpi-achievementdepartment-performancetop-performerslow-performersmanager-reviewpending-worklogs
  • Shared filters — employee, department, manager, designation, date range, month, quarter, year, KRA, KPI, rating band. The same filter component drives every report screen.
  • Queries read from snapshot tables wherever possible, never recomputing scores at report time.
  • Small results render synchronously and paged. Large exports are queued: the request returns a job id, the file is generated asynchronously with a streaming writer, and the user is notified when it is ready.
  • Formats — XLSX via Apache POI SXSSF, CSV streamed, PDF via a template engine with the company header and the filter set printed on the cover so an exported report is self-describing.
  • Every export is audited: who ran what, with which filters, and how many rows left the system.
Shipped, and the report module owns no SQL. Each definition is a bean declaring its key, permission, filter set and the module port that answers it; the registry indexes them at startup and refuses two reports claiming the same key. The queries live in the modules that own the data — WorkReportData, TaskReportData, KraReportData, PerformanceReportData, AppraisalReportData — and each applies the caller's access scope inside the query rather than filtering afterwards, so a mistake would be a wrong total rather than a data leak. The goal reports read the same scorecard the employee sees instead of re-deriving achievement in SQL, which is the only way a report and a screen stay in agreement. A result over the configured cap is refused with advice to narrow the filters rather than truncated into something that looks complete. Exports stream — SXSSF to disk for XLSX, a writer for CSV, and a PDF that prints its own filter set on the page — and every one writes a report_requests row naming who ran what, with which filters, and how many rows left the system. Only the person who ran an export may download it: the file holds rows from the scope they had at the time.
Section 23

Audit architecture

Two layers. Ambient audit columns (created_by, updated_by and timestamps) are filled by a JPA AuditingEntityListener on every table. Explicit audit is an AOP aspect on @Audited service methods that captures the before and after state and writes a row.

audit_logs
  id, company_id, actor_user_id, actor_name,
  action          CREATE | UPDATE | DELETE | APPROVE | REJECT |
                   FINALIZE | REOPEN | ADJUST | ASSIGN | EXPORT | LOGIN
  module          WORKLOG | KRA | PERFORMANCE | EMPLOYEE | SETTINGS ...
  entity_type, entity_id,
  old_value JSON, new_value JSON, changed_fields JSON,
  reason VARCHAR(500),          mandatory for ADJUST and REOPEN
  ip_address, user_agent, trace_id, created_at

Always audited

  • Employee created, deactivated, department or manager changed
  • KRA or KPI assigned, weightage changed, target changed
  • Work log approved, rejected, returned, or edited after submission
  • Any manual score adjustment, with previous and new score and reason
  • Performance finalised or reopened
  • Formula configuration or rating bands changed
  • Role or permission assignment changed
  • Login, logout, failed login, password reset, report export

Audit rows are insert-only — no update or delete path exists in code, and the application database user is not granted those privileges on the table. Retention is configurable with an archival job; nothing is deleted inside the retention window.

Shipped, insert-only by construction. The repository extends the bare Repository rather than JpaRepository, so delete and deleteAll do not exist on it — the trail is evidence, and inheriting a deletion path would leave it one autocomplete away. Every row carries the request's trace id, the same id that appears in the log line and comes back in the X-Trace-Id header. One deviation from the sketch: audit writing stayed as explicit auditService.record(...) calls at each site rather than an @Audited AOP aspect. The call sites name the module, the before and after values and the reason precisely; an aspect would have inferred them from method signatures and produced vaguer rows for the actions that matter most.

Deployment architecture

docker-compose.yml
  mysql      MySQL 8, named volume, healthcheck, init from Flyway on boot
  redis      cache for permissions, settings, formula config
  backend    Spring Boot fat jar, multi-stage Maven build, JRE 21 slim

  • Backend image — two-stage: maven:3.9-eclipse-temurin-21 builds, eclipse-temurin:21-jre-alpine runs as a non-root user with a container-aware heap setting.
  • Frontend image — node:20-alpine builds, nginx:alpine serves, with SPA history fallback and gzip.
  • Profiles — application-dev, application-test, application-prod. Every credential arrives as an environment variable: DB_URL, DB_USERNAME, DB_PASSWORD, JWT_SECRET, JWT_EXPIRY, REDIS_HOST, MAIL_*. The frontend reads VITE_API_BASE_URL.
  • Migrations — Flyway runs on startup; V1__baseline.sql onwards, with seed data (roles, permissions, default formula, rating bands, activity categories) as a separate repeatable migration.
  • Observability — Spring Actuator health and metrics, Logback JSON to stdout with a request trace id, scheduled-job outcomes recorded and surfaced on the admin dashboard.

Shipped, minus Redis and the mail server. Compose brings up MySQL with a healthcheck the backend waits on, the API as a multi-stage build running non-root with a container-aware heap, and the SPA behind Nginx with history fallback, gzip and X-Forwarded-For passed through so the rate limiter counts the caller rather than the proxy. Nothing in the compose file has a working default: it refuses to start without a .env, because a compose file that comes up with a known password is the one that reaches production unchanged. Two pieces of the sketch are honestly absent — Redis, because the caches and the limiter are in-process while this is one instance, and a mail container, because no mail sender is wired and the email channel records SKIPPED rather than pretending. Logging is key=value to stdout with the trace id on every line rather than JSON through a logstash encoder: greppable, parseable, and one fewer dependency. Testing gates are JUnit and Mockito over service logic; Testcontainers for repository tests is named in the README as the next thing CI should gain.
